# Playlist Canvas 릴리즈 노트 작성 가이드

> **AI 개발 도구 및 릴리즈 작성자 필독.** 이 문서는 GitHub Releases, docs/releases/ 아래의 버전별 문서, docs/release-notes/의 초안, 앱의 업데이트 안내에 적용되는 **사용자용 릴리즈 노트 작성 기준**입니다.
>
> **최우선 원칙: 개발자가 무엇을 구현했는지가 아니라 사용자가 무엇을 할 수 있게 되었고 무엇이 나아졌는지를 설명합니다.**

## 1. 독자와 목표

- 독자는 Python, Qt, FFmpeg, 렌더링 구조를 모를 수 있는 **일반 사용자**입니다.
- 릴리즈 노트를 읽고 30초 안에 **새 기능 / 편리해진 점 / 해결된 문제 / 업데이트 전 알아야 할 사항**을 이해할 수 있어야 합니다.
- 릴리즈 노트는 개발 일지, 커밋 요약, 테스트 보고서, 아키텍처 문서가 아닙니다.
- **한국어를 기본 언어**로 하며, 앱에서 실제로 보이는 기능명과 메뉴명은 정확히 사용합니다.

## 2. 반드시 지킬 작성 규칙

1. **사용자 체감 변화부터 씁니다.** 내부 기술이 아니라 새로운 조작 방법, 화면 변화, 성능이나 안정성의 실제 효과를 문장 앞에 둡니다.
2. **변경 사항을 중요도순으로 배치합니다.** 주요 신기능 → 사용성·속도 개선 → 오류 수정 → 설치·제한 사항 순서를 기본으로 합니다. 가장 큰 변화는 앞에 배치합니다.
3. **실제 동작을 구체적으로 적습니다.** '성능 향상', '안정화', 'UI 개선'이라는 문구만으로 끝내지 말고 무엇이 빨라지고, 어디가 바뀌고, 어떤 증상이 해결됐는지 설명합니다.
4. **기술 용어를 사용자를 위한 설명으로 번역합니다.** 렌더 작업자, 스레드 수명, 캐시 키, 픽셀 포맷, 필터 그래프, ONNX 분석기, 구현 클래스명, 내부 함수명, 단위 테스트 개수 등은 원칙적으로 사용자용 본문에서 제외합니다. FFmpeg·AutoMix·LRC·SRT처럼 사용자 설정과 직접 연결된 이름은 사용할 수 있습니다.
5. **나열을 위한 나열을 금지합니다.** 의미상 같은 변경 사항은 하나의 항목으로 합칩니다. 작은 내부 리팩터링과 테스트·패키징 변경 사항은 사용자에게 직접 영향이 없으면 생략합니다. 큰 릴리즈에서 중요한 기능을 억지로 생략하지는 않습니다.
6. **정확한 사실만 씁니다.** 변경된 코드, 이전 버전과의 차이, 테스트 결과 또는 기존 공식 문서로 확인되지 않은 기능·오류 수정·속도·수치를 만들지 않습니다. 의심스러우면 확인하고, 확인할 수 없으면 쓰지 않습니다.
7. **성능 수치는 조건과 함께 씁니다.** 속도 향상 수치를 적는 경우 테스트 해상도·FPS·길이·측정 범위를 함께 밝히고 모든 PC에서 동일하다고 표현하지 않습니다. 근거 없는 '2배 빠름', '완전히 해결', '메모리 50% 절감' 등은 금지합니다.
8. **사용자에게 중요한 불편과 제약을 숨기지 않습니다.** 베타 기능, FFmpeg 필요 여부, 호환성 변경, 제거된 기능, 기존 프로젝트 영향, 저장 공간 사용과 알려진 문제를 필요한 버전에 유지합니다. 과거 버전은 **해당 버전 출시 당시의 상태**를 기록합니다.
9. **버전별 실제 범위만 다룹니다.** 다음 버전에서 해결된 문제를 이전 버전에서 해결됐다고 쓰지 않습니다. 이전 릴리즈의 문제를 나중에 수정했다면 수정된 버전에 명시합니다.
10. **자연스럽고 정확하게 씁니다.** 간결한 존댓말을 사용하며 과한 마케팅 문구, 반복적인 과장, 어색한 번역체, 장황한 내부 구현 설명을 피합니다.
11. **설치 안내는 실제 배포 방식에 맞게 씁니다.** 자동 업데이트 가능 여부, 필요한 외부 프로그램, 설치본 이름과 경고는 버전별로 확인합니다. 현재 버전의 설치 방식을 첫 버전에 소급하지 않습니다.
12. **GitHub 릴리즈 수정은 범위를 제한합니다.** 사용자가 릴리즈 설명 변경을 요청했다면 태그·첨부 파일·공개 상태·다운로드 링크·릴리즈 날짜는 임의로 변경하지 않습니다.

## 3. 기본 Markdown 구조

규모에 맞게 섹션 수와 항목 수를 조절합니다.

### 새 기능이 있는 일반 업데이트

    # Playlist Canvas 1.x.x.x

    이번 업데이트에서는 [핵심 변화]를 추가하고 [주요 문제]를 개선했습니다.

    ## 새로운 기능
    - **기능 이름:** 사용자가 어디에서 무엇을 할 수 있는지 설명합니다.

    ## 개선 및 오류 수정
    - 사용자가 겪었던 문제와 해결 결과를 설명합니다.

    ## 설치 및 참고
    - 업데이트 방법, 베타 여부, 필요한 프로그램과 주의 사항을 안내합니다.

### 오류 수정 위주의 소규모 업데이트

    # Playlist Canvas 1.x.x.x

    [사용자가 겪던 핵심 문제]를 해결한 업데이트입니다.

    ## 수정 사항
    - **문제 해결:** 문제가 나타나던 상황과 수정 결과를 적습니다.

    ## 참고
    - 꼭 필요한 호환성·설치 안내만 포함합니다.

- 소규모 패치는 **중요한 내용 3~6개 안팎**, 주요 버전은 **핵심 변경 사항 6~14개 안팎**을 우선 고려합니다. 실제 중요한 변화가 많다면 충분히 설명하되, 중복과 내부 구현은 줄입니다.
- 한 항목에는 가급적 하나의 사용자 관점 변화만 담습니다.
- '내부 구조 개선', '테스트 및 검증', '배포 검증'을 사용자용 릴리즈의 독립적인 대형 섹션으로 만들지 않습니다. 공개 테스트 결과가 필요한 경우 간단한 참고로 적거나 별도 기술 보고서로 분리합니다.

## 4. 나쁜 예시 → 좋은 예시

### 예시 A. 영상 내보내기 속도

**나쁨**
> 독립적인 Canvas 레이어를 별도의 렌더 작업자에서 동시에 생성하고 FFmpeg 파이프의 대기 시간을 감소시켰습니다.

**좋음**
> **영상 내보내기 속도 개선:** 여러 화면 요소가 있는 영상도 더 빠르게 저장할 수 있도록 처리 과정을 개선했습니다. 화질과 프레임 수는 그대로 유지합니다.

### 예시 B. AutoMix 음량 오류

**나쁨**
> FFmpeg 로그 버퍼 앞부분 유실로 인한 loudness normalization 파싱 결과 불일치를 수정했습니다.

**좋음**
> **AutoMix 음량 오류 수정:** 일부 곡에서 미리듣기와 최종 영상의 음량이 다르게 나올 수 있던 문제를 해결했습니다.

### 예시 C. 미리보기 화면 멈춤

**나쁨**
> Qt 작업 스레드 정리 과정에서 메인 이벤트 루프를 블로킹하던 동기 대기를 제거했습니다.

**좋음**
> **탭 전환 시 멈춤 해결:** 미리보기에서 플레이리스트나 타임라인 탭으로 이동할 때 화면이 오래 멈추던 문제를 수정했습니다.

### 예시 D. 실제로 추가한 기능

**나쁨**
> 오디오 스트림만 FFmpeg 출력 경로에 전달하도록 인코딩 브랜치를 추가했습니다.

**좋음**
> **오디오만 내보내기:** 영상 없이 플레이리스트를 MP3·M4A·WAV·FLAC·OGG 파일로 저장할 수 있습니다.

위 예시의 문장은 **표현 방식의 예시**입니다. 기능이 현재 개발 중이라는 이유만으로 릴리즈에 추가하지 마세요. 반드시 해당 버전에서 실제로 제공되는지 확인하세요.

## 5. 작성 전 확인할 근거

릴리즈를 작성하기 전에 다음 내용을 확인합니다.

1. **대상 버전과 직전 버전의 실제 차이:** Git 태그 비교, 관련 코드·설정 및 변경 기록.
2. **사용자에게 보이는 상태:** 실제 메뉴·버튼·설정 이름, 기본값, 지원 파일 형식, 사용 방법.
3. **해당 버전의 해결 범위:** 알려진 문제, 베타 상태, 제약, 호환성 및 오류 수정 여부.
4. **배포·설치 상태:** 자동 업데이트와 FFmpeg 요구 사항, 설치 파일, 제거된 기능, 프로젝트 호환성.
5. **성능 주장 근거:** 측정 조건, 비교 범위 및 재현 가능한 결과.

근거가 부족한 항목은 표시해 검증하거나 제외합니다. 추측으로 사용자에게 기능을 약속하지 않습니다.

이 저장소의 기존 릴리즈 예시는 docs/release-notes/1.0-1.1.json, 1.2.json, 1.3.json에 정리돼 있습니다. 새 버전은 이 문서와 기존 사용자 중심 릴리즈의 어조를 일관되게 유지하세요. 단, 과거 문서도 항상 사실 검증을 우선합니다.

## 7. AI 에이전트에게 주는 직접 지시

릴리즈 설명을 만들거나 수정하라는 요청을 받으면:

1. 이 문서를 먼저 읽습니다.
2. 사용자 관점의 핵심 변화부터 식별합니다.
3. 변경 사항을 실제 코드와 배포 상태로 확인한 후 위 구조로 작성합니다.
4. 초안을 검수 체크리스트에 따라 스스로 다시 점검합니다.
5. 기술 상세가 꼭 필요하면 사용자용 릴리즈와 **별도의 개발자 변경 기록**으로 분리합니다.
6. 사용자가 공개 반영을 명시하지 않았다면, 초안 또는 PR을 먼저 만들고 실제 릴리즈 게시·수정을 임의로 실행하지 않습니다.

**기억할 문장:** "무엇을 어떻게 개발했는가"보다 **"업데이트하면 사용자에게 무엇이 달라지는가"**를 먼저 설명하세요.
