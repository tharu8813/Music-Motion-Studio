# 타임라인 정밀 입력 및 모션 편집기 안정화 검증

2026-11-04, Windows 네이티브 Qt 검증. 기준 커밋은 `0183459ce618d3af18c38eb103128adf9cca49e3`이다. 버전, 릴리즈, 프로젝트 저장 형식은 변경하지 않았다.

원시 측정값과 모듈별 테스트 결과는 [검증 JSON](benchmarks/2026-11-04-precision-timing-motion-stability.json)에 보존했다. 아래 수치는 이번 작업에서 실제 실행한 결과다.

## 1. 실제로 확인한 문제

- 시각 타임라인에는 정확한 시간값을 입력하는 진입점이 없었다.
- 기존 드래그와 방향키는 지속 시간을 소수 둘째 자리로 반올림했다. 밀리초 정밀 입력을 추가한 뒤에도 이 경로를 그대로 두면 사용자가 입력한 길이가 다음 이동에서 바뀐다.
- `render_now()`를 직접 호출해도 예약된 단발 타이머가 남아 같은 상태를 다시 캡처할 수 있었다.
- 200점 시간축은 매번 모든 마커의 Qt 객체와 도형을 만들어 다시 그렸다.
- 같은 영상 파일의 seek에서는 필터 작업 세대가 바뀌지 않았다. 이전 시각에서 시작한 비동기 필터 결과가 새 시각에 반영될 수 있었다. 원본 디코더의 프레임 시간도 모션 편집기에서 검증하지 않았다.
- 기존 영상 안내는 비동기 동기화와 정지 화면 대체를 한 문장으로 설명해, 실제 로딩 상태를 구분하기 어려웠다.

오디오 캐시에서는 이번 검증으로 새 결함이 확인되지 않았다. 기존의 두 항목 제한과 파일 지문 무효화를 유지했다.

## 2. 정밀 시간 편집 방식

막대 우클릭의 **시간 정밀 편집...** 또는 타임라인에 초점을 둔 **F2**로 작은 팝오버를 연다. 선택 막대 아래를 기준으로 배치하고 화면 경계 안으로 보정한다. 오류 안내 때문에 크기가 커질 때도 위치를 다시 보정한다. 더블클릭 확대는 유지한다.

| 대상 | 편집 규칙 |
| --- | --- |
| 음악 | 시작만 편집한다. 종료와 원본 재생 길이는 읽기 전용이다. 최소 시작은 `PlaylistService.minimum_start_time()`을 따른다. |
| 요소 시작 | 기존 지속 시간을 유지한다. |
| 요소 종료 | 시작을 유지하고 `종료 - 시작`을 지속 시간으로 사용한다. |
| 요소 지속 시간 | 시작을 유지한다. 일반 길이는 0보다 커야 한다. |
| 곡 끝까지 표시 | 별도 체크 상태로 표현하고, 저장 값 `timeline_duration == 0`을 유지한다. 시작을 옮겨도 일반 0초 클립으로 변환하지 않는다. |

`12.50`, `01:23.45`, `01:23.450`, `01:02:03.500`을 지원한다. 음수, 잘못된 구분 형식, 콜론 뒤의 분·초가 60 이상인 값, 비유한 값, 시작보다 이른 종료를 차단한다. 내부 모델은 기존 float 초 단위를 유지한다. 문자열 계산에는 Decimal을 사용하고 입력을 두세 자리로 강제 반올림하지 않는다. float 표현 범위를 넘는 정밀도를 새로 제공하는 것은 아니다.

초점을 옮기면 팝오버 안의 임시 값과 파생 표시를 갱신한다. **적용/Enter**에서만 프로젝트에 반영한다. **취소/Escape/바깥 클릭**은 초안을 버린다. 기본값은 선택 항목의 현재 시간이다. 입력 중 저장 상태와 자동 저장 데이터는 바뀌지 않는다.

정밀 입력과 드래그는 `TimelinePanel._commit_visual_timing()`을 공유한다. 변경 전후에 기존 History의 보류 작업을 확정해, 빠른 연속 적용도 각각 하나의 Undo가 된다. 값이 같은 적용은 변경 신호를 내지 않는다. 선택과 스크롤은 유지하며, 이동 작업에서는 기존의 정밀 지속 시간을 보존한다.

## 3. 기존 기능 및 저장 호환성

간단/고급 모드, 독립 속성 곡선, 베지어, 시작/끝 자세 연결, Canvas 이동·크기·회전, 로컬/프로젝트 Undo와 적용/취소를 유지했다. 기존 모션과 프리셋, AutoMix·크로스페이드, CPU/GPU 렌더 및 FFmpeg 출력 경로를 변경하지 않았다.

프로젝트 시간 필드와 애니메이션 저장 구조도 그대로 사용한다. 정밀 시간의 실제 `.pvsproj` 저장·재열기, 기존 모션 저장·복원, Canvas/실제 MP4 및 네이티브 GPU 비교 테스트를 실행했다. 범용 키프레임 UI나 옛 숫자 편집 탭은 복원하지 않았다. 기존 디자인 시스템을 그대로 사용한다.

## 4. 성능 진단과 선택한 수정

`tools/profile_motion_editor.py`는 기존 네이티브 품질 하네스를 실행하면서 다음 구간을 별도 계측한다.

1. 키프레임 평가와 자세 계산
2. CanvasSnapshot 캡처와 실제 Scene 렌더
3. QImage→QPixmap 변환
4. 이미지 필터와 영상 프레임 콜백
5. 영상 시각 요청과 음악 반응 조회
6. 재생 타이머, 위젯 갱신, 키프레임 시간축 그리기

계측은 GUI 벽시계 시간이며 구간끼리 중첩된다. 합산한 값이 전체 지연은 아니다. GPU 실행 시간이나 백그라운드 필터 작업 전체 시간을 뜻하지도 않는다. 비활성 앱 실행에 프로파일러를 상시 삽입하지 않았다.

실제 비용이 확인된 두 부분을 수정했다.

- 직접 렌더가 보류 타이머 요청을 소비한다. 기존 16ms 최신 상태 병합은 유지한다.
- 마커 그림 하나만 시간축 위젯마다 캐시한다. 키 시각, 실제 선택된 점, 활성 상태, 편집 가능한 점, 크기, 표시 범위, DPI, 색상이 달라지면 다시 만든다. 재생 커서는 별도로 그린다. 화면 DPI 그대로 생성하며 애니메이션 데이터의 정밀도·프레임레이트나 Canvas 화질은 낮추지 않는다.

겹치는 마커를 벡터 경로로 묶었던 후보는 실제로 더 느려 제거했다. QImage→QPixmap 변환과 키프레임 평가는 작은 비용이어서 추가 캐시를 도입하지 않았다. 전체 Scene 캐시는 변경된 영상·오디오·소스 상태를 오래된 이미지와 혼동할 위험에 비해 이번 측정에서 이득이 충분히 입증되지 않아 도입하지 않았다.

## 5. 최적화 전후 측정과 한계

환경: Windows 11 build 26300, Python 3.14.10, PySide6 6.12.0, FFmpeg 9.0.2. 한국어, DPI 100%, 3840×2160 Canvas, 53요소(영상 1개 포함), 모션 200점, 탐색 100회, 편집 창 열기·닫기 20회다. 재생 타이머도 실행한다. 열기 시간에는 하네스의 100ms 재생 확인이 포함된다. 탐색 표본은 첫 주기의 간단 모드에서 얻고, 고급 모드는 별도로 측정했다.

| 실행 | 중앙값 ms | 95백분위 ms | 최대 ms |
| --- | ---: | ---: | ---: |
| 최초 실제 변경 전 소스 | 13.88 | 17.63 | 33.34 |
| 제거한 벡터 경로 후보 | 15.07 | 18.67 | 42.92 |
| 마커 캐시 적용 직후 중간 결과 | 9.81 | 12.16 | 36.88 |
| 최종 코드의 첫 재측정 | 11.27 | 24.92 | 34.43 |
| 같은 시점의 변경 전 경로 재실행 | 26.59 | 42.87 | 53.67 |
| 바로 이어 실행한 최종 코드 | 11.53 | 23.90 | 36.90 |

마지막 연속 비교의 변경 전 실행은 `--baseline`으로 HEAD의 변경 대상 렌더·미디어 메서드를 메모리에서 복원한 것이다. 작업 파일을 되돌리지는 않는다. 생성자는 최종 클래스와 추가된 미사용 필드를 유지하므로, 전체 체크아웃을 별도로 실행한 결과와는 구분한다. 최초 변경 전 수치는 실제 수정 전 소스로 실행했다.

연속 비교에서는 중앙값 약 56.6%, 95백분위 약 44.2% 감소했다. 그러나 최초 변경 전 17.63ms와 최종 23.90ms를 비교하면 95백분위가 더 높다. 실행 시점에 따라 Scene 렌더와 위젯 비용 자체가 크게 달라졌다. 동일 하네스라도 환경 편차가 컸으므로, 모든 환경에서 일정한 개선이나 60fps를 보장한다는 결론은 내리지 않는다. 과거 요청서의 13.19/38.67/56.86ms를 이번 실행 결과로 사용하지 않았다.

연속 비교의 세부 구간별 중앙값/95백분위/최대값은 검증 JSON에 모두 있다. Scene 자체의 중앙값은 7.547→7.588ms, 캡처는 9.823→9.904ms로 빨라지지 않았다. 마커 그리기 중앙값은 3.874→0.271ms로 줄었다. 전체 하네스의 캡처 호출은 484→346회였다. 비동기 영상과 타이머 도착 수는 실행마다 달라지므로 호출 수를 고정 비율의 보장으로 해석하면 안 된다.

최종 보조 측정도 모두 4K Canvas, 100회 탐색, 3회 열기·닫기다.

| 구성 | 중앙값 ms | 95백분위 ms | 최대 ms |
| --- | ---: | ---: | ---: |
| 5요소·영상 없음 | 6.06 | 7.74 | 8.95 |
| 18요소·영상 1개 | 9.99 | 16.54 | 35.02 |
| 53요소·고급 모드 | 12.73 | 24.91 | 42.33 |
| 55요소·영상 3개 | 29.54 | 49.98 | 93.00 |

영상 3개 구성에서는 지연이 남는다. 여러 비동기 디코더의 프레임 처리와 전체 Scene 캡처가 남은 비용이며, 이번 작업으로 해결됐다고 보고하지 않는다.

연속 비교의 닫은 뒤 RSS는 변경 전 346.99→393.09MiB, 최종 347.86→384.65MiB였다. 마지막 10주기 범위는 각각 380.97~393.09MiB, 379.12~384.65MiB다. 최종 실행의 RSS가 더 낮고 후반 범위도 좁았지만, 두 실행 모두 처음보다 증가했다. Qt·디코더·렌더 캐시별 잔류량은 분리 측정하지 않았으며, 20회 측정만으로 장시간 누수가 없다고 증명하지 않는다. 모든 주기의 디코더 해제와 원본 데이터 보존 검사는 통과했다.

## 6. 영상 프레임 동기화

모든 seek에서 필터 작업 세대를 무효화한다. 모션 편집기의 복제 디코더에서는 추가로 다음을 수행한다.

- 새 seek 때 이전 표시 프레임을 비우고 로딩 상태로 표시한다.
- 프레임 수신 시 요청 시각과 PTS를 비교한다. 필터가 늦게 끝난 경우에도 최신 시각으로 다시 검사한다.
- 정상 재생 중에도 제시된 프레임 시각이 요청 범위를 벗어나면 로딩 상태로 구분한다.
- 재생 중 불연속 탐색은 편집기용 허용 범위로 감지한다. 기존 메인 미리보기의 정상 재생 교정 정책은 유지한다.
- 닫기·소스 전환·새 seek 이후의 오래된 결과가 새 상태로 반영되지 않도록 한다.

`MotionPreviewMedia`가 소스별 **로딩 중 / 동기화 / 정지 화면 / 미지원·시간 확인 불가** 상태를 모아 간결하게 표시한다. 숨긴 요소는 상태 집계에서 제외한다. 실제 디코더 오류와 길이 확인 실패도 구분한다. 반복 팝업은 띄우지 않는다.

빠른 연속 요청, 반복 시작점 복귀, 곡 시작/끝, 곡 변경, 여러 소스, 프록시 경로, 지연 필터, 메타데이터 작업 중 닫기, 동기화 ON/OFF와 QMediaPlayer/QVideoSink 정리를 검증했다. 일부는 결정적인 모의 지연·프록시 경로 테스트이며, 실제 H.264 seek/반복 및 GPU/CPU 비교도 별도로 실행했다.

이는 비동기 미리보기이며 모든 코덱의 프레임 단위 정확성을 보장하지 않는다. 기존 디코더 허용 범위는 30fps 설정에서 160ms이며, PTS가 없으면 동기화 완료로 표시하지 않는다. 기존 프록시를 재사용하고 편집기에서 새 프록시는 만들지 않는다.

## 7. 음악 반응 지원 범위

배경의 저음 반응과 텍스트·가사의 음악 반응은 완료된 분석 캐시가 있으면 실제 값을 사용한다. 캐시가 없거나 해당 반응 프로필이 없으면 예시값을 사용한다. 오디오 시각화·파형·레벨 미터·파티클은 기존 예시 미리보기를 유지한다. 실제 분석, 예시, 혼합 상태는 기존 안내로 구분한다.

캐시는 최대 두 항목이고 읽기만으로 분석을 시작하지 않는다. 키는 곡 ID·정규화 파일 경로·파일 크기·수정 시각이다. 동일 파일을 쓰는 다른 곡, 파일 교체·삭제, 재분석 결과 교체와 세 번째 곡에 의한 교체를 검증했다. 별도의 시간 TTL은 없으며, 만료는 항목 교체와 파일 지문 불일치로 처리된다. 새 분석 엔진이나 무제한 캐시는 추가하지 않았다.

## 8. 책임 분리와 변경 파일

새 `PrecisionTimeDialog`에 입력 해석·검증·임시 시간 관계만 분리했다. `TimelinePanel`은 모델 적용과 History 경계, `VisualTimeline`은 진입점과 제스처를 담당한다. 영상 결과 유효성은 기존 `SourceItem`, 영상 상태 집계는 기존 `MotionPreviewMedia`, 시간축 그림 캐시는 해당 위젯이 담당한다.

모션 초안은 이미 불변 `CustomMotion`과 로컬 Undo로 관리되며, 미디어 수명도 기존 보조 객체에 분리되어 있다. 이번 수정에 추가적인 대형 Draft/Preview Controller 추출이 꼭 필요하지 않아 수행하지 않았다. Signal 연결과 수명을 넓게 바꾸는 리팩터링도 피했다.

- 앱: `app/timeline/precision_time_dialog.py`, `timeline_panel.py`, `visual_timeline.py`; `app/dialogs/custom_motion_dialog.py`, `motion_preview_media.py`, `motion_timeline.py`; `app/canvas/source_item.py`; `app/ui/main_window.py`.
- 테스트: `tests/test_precision_timing.py`, `test_motion_preview_stability.py`, `test_visual_timeline.py`, `test_custom_motion_dialog.py`.
- 도구: `tools/profile_motion_editor.py`, `verify_motion_editor_quality.py`, `verify_precision_timing_ui.py`.

최초 관련 테스트 실행에는 샌드박스 임시 폴더 접근 오류와 그에 따른 시간 초과가 있었다. 저장소의 `work/test-temp`로 TEMP/TMP/TMPDIR을 지정한 재실행은 통과했다. 전체 실행의 로그인 시간 초과는 로컬 HTTP 연결 차단 때문이며, 별도 재실행 결과를 원래 전체 실행의 성공으로 바꾸어 적지 않았다. 건너뛴 항목을 통과로 세지 않았다.

재현 예시(PowerShell, 저장소 루트):

```powershell
$env:TEMP = (Resolve-Path work/test-temp).Path
$env:TMP = $env:TEMP
$env:TMPDIR = $env:TEMP
.venv\Scripts\python.exe scripts/run_tests.py --report work/full-suite.json
.venv\Scripts\python.exe tools/profile_motion_editor.py --baseline --output work/before --samples 100 --cycles 20
.venv\Scripts\python.exe tools/profile_motion_editor.py --output work/after --samples 100 --cycles 20
```

`--baseline`은 이 보고서의 기준 HEAD에서만 비교 의미가 같다. 이후 커밋에서는 당시 메서드를 별도로 고정해야 한다. 네이티브 추가 검증은 `QT_QPA_PLATFORM=windows`, 실제 FFmpeg 경로, `PLAYLIST_CANVAS_RUN_PREVIEW_SOAK=1`을 지정했다. 전체 일반 실행과 별도로 순차 실행한다.

## 10. 남은 문제와 제한

- 여러 영상이 포함된 복잡한 4K 구성의 순간 지연은 남아 있다. Scene 렌더 자체는 빨라지지 않았다.
- 성능 수치는 실행 시점에 따라 크게 달랐다. 최초 기준 대비 최종 95백분위의 일관된 개선은 입증하지 못했고, 같은 시점의 변경 전 경로와 연속 비교했을 때 개선을 확인했다.
- 20회 열기·닫기와 네이티브 장시간 검사를 통과했지만, 모든 프로젝트에서 장기 메모리 증가가 없다는 보장은 하지 않는다.
- 비동기 디코더 허용 범위 안의 미리보기다. PTS 미제공, 매우 낮은 프레임레이트나 특이한 코덱에서 프레임 단위 정확성은 보장하지 않는다.
- 음악 시각화·파티클은 예시 지원 범위를 유지한다. 분석 캐시가 없는 효과는 실제 분석처럼 표시하지 않는다.
- 67개 선택적·환경 의존 테스트는 여전히 건너뛰었다. 모든 외부 서비스·모델·하드웨어 조합을 검증한 결과는 아니다.
