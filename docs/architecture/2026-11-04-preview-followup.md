# Music Motion Studio 미리보기·프로젝트 성능 후속 검증

이번 단계는 사용자가 요청한 영상 내보내기 보류를 반영해 실시간 미리보기, AutoMix 미리 듣기,
프로젝트 열기와 프로그램 시작을 대상으로 했다. 이전 단계의 출력 품질과 인코딩 수치는 별도
보고서에 기록했다. [이전 단계 보고서](2026-11-04-pipeline-performance.md)

## 적용한 변경

| 변경 | 원인과 적용 방법 | 검증과 제한 |
| --- | --- | --- |
| 미리보기 표시 주기 | `app/preview/cadence.py`의 `screen_preview_fps`와 `ExportPreviewDialog._sync_presentation_cadence`가 표시 주기를 현재 미리보기 화면의 주사율에 맞춘다. 커스텀 모션과 가사 애니메이션 미리보기도 화면 기준 타이머를 사용한다. 디코더의 60 FPS 상한을 해제하고 부하가 큰 경우의 프레임 조절은 유지했다. | 실제 144 Hz 화면, 모의 144→60 Hz 전환, 일시정지와 탐색을 검증했다. 오디오 분석·일부 오버레이의 30 Hz 샘플은 별도다. |
| 영상 프록시 타이밍 | `PreviewProxyWorker.run`에서 30 FPS 강제 변환을 제거하고 영상 크기만 줄인다. FFmpeg에 원본 타임베이스와 프레임 타이밍 보존을 요청한다. 프록시 캐시 키가 바뀌며 기존 프록시는 같은 용량 한도 내에서 정리된다. | FFmpeg/FFprobe로 59.94 FPS와 가변 프레임률 클립의 전체 프레임 수와 표시 타임스탬프를 대조했다. MPEG-4 대체 인코더는 1/60000초 단위로 시간을 기록한다. |
| 영상과 GPU 자원 | `SourceItem._configure_video_preview`에서 숨겨진 영상의 디코더 생성을 피하고 파일·표시 상태가 바뀌면 대기 프레임을 비운다. `motion_preview_media.py`에서는 타임라인 밖의 미디어 탐색을 피한다. `GpuTexturePreviewSurface._evict_texture_cache`는 최근 사용 순서만 비교한다. | 레이어의 문자열 키와 튜플 키가 같은 프레임에 쓰이면 텍스처 정리 중 예외로 CPU에 폴백하던 문제를 재현했다. 수정 후 1080p와 4K 통합 장면에서 GPU를 유지했고, 모의 컨텍스트 손실에서는 CPU 폴백을 확인했다. |
| AutoMix 음량 분석 | `playlist_gain`은 같은 파일 경로의 FFmpeg EBU R128 작업을 한 번만 예약하고 각 곡 항목의 시간과 볼륨은 기존 방식으로 집계한다. | 같은 파일을 네 곡 항목에 사용한 경우의 탐색 횟수와 최종 게인을 비교했다. Basic 리듬 분석이나 전환 계획 속도에 이 수치를 적용할 수 없다. |
| 시작·프로젝트 열기 | `source_item.py`는 첫 블러 효과에 SciPy를 가져온다. `ProjectMediaService.validate`는 한 번의 검증 안에서 같은 경로의 파일 확인을 재사용한다. | 빈 프로젝트, 일반 프로젝트와 대형 프로젝트를 실제 편집기에서 복원했다. 경로 확인은 다음 검증에서 다시 수행한다. SciPy 로딩 비용은 해당 효과를 처음 쓰는 시점에 발생한다. |

## Windows 네이티브 미리보기

Windows 11, Qt 6.12.0, OpenGL 3.3과 RTX 5060에서 합성 미디어로 실행했다. 표의 FPS는 GPU 화면
교체 콜백 중 실제로 새 장면을 표시한 횟수다. P95는 연속 표시 간격이며 클릭에서 화면까지의
입력 지연은 별도로 측정하지 않았다. CPU는 앱 프로세스가 평균 사용한 논리 코어 수로 환산했다.
GPU 텍스처는 앱의 추적값이며 GPU 사용률과 전체 VRAM은 계측 범위 밖이다.

| 장면 | 표시 목표 | 새 장면 FPS | 표시 간격 P95 | 앱 CPU | 앱 RSS 최고 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 640×360/60 영상 한 개, 실제 144 Hz 모니터 | 144 FPS | 58.1 | 30.9 ms | 0.49코어 | 407 MiB |
| 1080p 통합 미리보기 | 60 FPS | 51.8 | 44.8 ms | 3.40코어 | 1.24 GiB |
| 4K 통합 미리보기, 영상 3개 | 60 FPS | 33.0 | 60.6 ms | 3.61코어 | 1.37 GiB |

각 장면은 3초 예열과 약 8초의 측정을 1회 실행했다. 통합 장면은 곡 3개, 한영 가사, 커버,
Now Playing, 커스텀 모션과 시각화 요소를 포함했다. 4K에는 파티클과 음악 반응 텍스트를
추가했다. 두 통합 장면 모두 실제 혼합 오디오 준비와 `beat_match / vocal_safe_eq` 전환 2개를
확인했다. 영상은 각각 1개와 3개의 미리보기 프록시를 사용했다. 같은 통합 장면을 이전 30 FPS
프록시로 측정한 1회 실행은 1080p 69.2 FPS, 4K 54.7 FPS였다. 프레임 타이밍을 보존하는 현재
프록시는 60 FPS 원본의 프레임을 유지해 디코딩·업로드 부하가 커질 수 있다. 이 실행에서 4K
앱 CPU 사용량은 1.96→3.61코어였다.

원본 해상도 영상 3개를 동시에 디코딩하는 경로에서 새 장면 FPS는 기준 3회 7.5~8.1,
최종 2회 8.2~9.1이었다. GUI 프레임 콜백 P95는 21.1~25.1ms에서 19.9~20.9ms로 변했다.
픽셀 변환을 작업자 스레드로 옮긴 실험은 콜백을 줄였지만 RSS가 늘었고 세 번째 실행이
멈춰 되돌렸다. 전체 해상도에서 디코딩된 CPU 프레임을 이미지로 변환하고 GPU에 업로드하는
구간이 계속 병목이다.

## 시작·프로젝트·AutoMix 전후 비교

| 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 새 Python 프로세스에서 편집기 사용 준비, 중앙값 | 2.086초 | 1.418초 |
| 빈 프로젝트 열기, 중앙값 | 32.1 ms | 35.7 ms |
| 일반 프로젝트 열기, 중앙값 | 47.7 ms | 41.9 ms |
| 대형 프로젝트 열기, 중앙값 | 450.0 ms | 314.7 ms |
| 대형 프로젝트 미디어 검증, 중앙값 | 39.2 ms | 19.5 ms |
| 같은 파일 네 항목의 AutoMix 음량 분석, 콜드 중앙값 | 74.48 ms | 59.44 ms |
| 순서를 바꿔 다시 음량 계산, 웜 중앙값 | 2.42 ms | 0.79 ms |

시작과 프로젝트는 같은 Windows의 Python 소스 실행에서 각 3회 측정했다. 시작 수치에서
실행 파일 로더 시간은 제외했다. 대형 프로젝트는 이미지·모션 요소, 영상 3개, 곡 항목
100개, 한영 가사 1,000개를 포함했다. 음량 분석은 각 3회 실행했고, 최초 FFmpeg 분석 횟수가
4→1회로 줄었으며 최종 선형 게인은 모든 실행에서 2.8840315031266055로 일치했다.

## 회귀·안정성 시험

- 미리보기·프로젝트·AutoMix 관련 집중 회귀 실행 282건 중 277건 통과, 5건 건너뜀.
- 최종 프록시 테스트 7건 통과. 앞선 집중 회귀의 프록시 항목과 일부 중복된다.
- 네이티브 GPU 및 전체 화면 시험 32건 중 30건 통과, 2건 실패. 60초 연속 재생은 영상 루프
  10회, 탐색 15회, 수락 프레임 1,805개, 압력 드롭 3개로 통과했다. 예열 후 RSS 증가
  관측 최대는 0.10 MiB였다.
- 20회 열기·일시정지·탐색·재생·종료에서 매회 텍스처 할당이 0으로 돌아갔고 디코더와
  작업자 참조가 해제됐다. RSS는 첫 종료 후 대비 통합 실행에서 75.5 MiB, 격리 재실행에서
  130.3 MiB 증가해 두 번 모두 64 MiB 기준을 넘었다. 현재 코드의 표시 주기만 30 FPS로
  고정한 대조 실행에서도 89.0 MiB 증가했다. GPU 위젯을 종료 때 분리하지 않는 실험은
  반복 실행 중 멈춰 기존 종료 방식으로 되돌렸다.
- 포인터 이벤트 없이 커서 이동을 감지해 전체 화면 컨트롤을 다시 표시하는 검사는 네이티브
  환경에서 실패했으며, 30 FPS 주기 대조 실행에서도 재현됐다. 모의 포커스 전환, GPU 컨텍스트
  복원과 전체 화면 종료 검사는 통과했다.

## 후속 검증이 필요한 항목

1. 4K 원본 영상 여러 개를 동시에 재생할 때 이미지 변환·업로드 병목, 실제 입력 지연 및 GPU
   사용률. 60 FPS 원본을 유지한 프록시에서 4K 통합 장면의 처리량도 개선 여지가 있다.
2. 반복 열기에서의 RSS 증가 원인, 전체 화면 포인터 검사 실패, 실제 다중 모니터·배율 전환
   및 드라이버 수준 컨텍스트 손실.
3. AutoMix Beat This/ONNX와 Sonara의 분석 비용, 부분 전환 계획 재사용. 설치판 시작과 실제
   대형 프로젝트의 장시간 편집.
4. 영상 내보내기 최적화와 재측정은 사용자 요청에 따라 보류했다.
