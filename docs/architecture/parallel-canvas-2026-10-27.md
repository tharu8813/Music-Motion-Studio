# Canvas 내보내기 병렬화

기존에는 GUI 스레드가 각 Z 밴드의 다음 화면을 순서대로 만들었다. FFmpeg가 입력을
기다리는 병목을 줄이기 위해, 서로 독립적인 Canvas 밴드는 별도 Qt 프로세스에서 만든다.
편집기와 저장 파일 구조는 바꾸지 않는다.

## 실행 경계

- `ExportSession`은 기존 타임라인·coalescing·CFR 시간 계산과 Z 순서를 유지한다.
- 각 `CanvasProcessStream`에는 소스의 저장 값, 등록 글꼴 경로, 트랙, 저음 envelope,
  완료된 가사 간주 분석 결과를 전달한다. Qt 장면과 QPixmap은 프로세스 안에서만 사용한다.
- 작업자 내부의 `ExportCanvasCapturer`가 기존 `CanvasSnapshot`으로 화면을 만들고
  기존 `PipedCanvasStream`으로 FFmpeg에 바로 쓴다. 큰 QImage를 부모에게 왕복하지 않는다.
- 부모는 길이가 제한된 샘플 큐(2개)에 작업을 전달하고, 작업자는 기존 이미지 큐(2개)를
  사용한다. 큐 대기 중 UI를 처리하고, 취소·최종 인코더 실패·파이프 정지를 확인한다.
  큰 초기 분석 배열도 큐의 전송 스레드로 보내 프로세스 시작 인수의 동기 전송에서 제외했다.
- 작업자 오류와 비정상 종료를 부모에게 전달한다. 실패 시 전체 작업자를 정리하며,
  기존 내보내기의 중간 파일 경로로 되돌아가는 정책을 유지한다.
- Windows 설치본도 `freeze_support()`를 거쳐 렌더 작업자만 실행한다. 새 편집기 창을
  띄우거나 별도의 프로젝트를 열지 않는다.

프로세스별 글꼴 등록이 빠진 초기 시제품에서 글자가 깨지는 문제가 있었으므로, 기존
`apply_studio_style`과 편집기에 등록된 글꼴 경로를 작업자에서도 사용한다. 해당 시제품의
시간은 최종 성능 비교에서 제외했다. 가사 분석도 재요청하지 않도록 완료한 Future의
결과를 보관해 소스·트랙별 읽기 전용 스냅샷으로 사용한다.

## 적용 범위

5초 이상이고 비고정 Canvas 스트림이 2–4개인 파이프 내보내기에 적용한다. 작업자 수는
논리 CPU 수의 절반을 넘지 않는다. 한 스트림, 짧은 작업, 많은 스트림 또는 작은 CPU의
경우 기존 GUI 캡처 경로를 사용한다. 고정 이미지는 기존 단일 PNG 경로를 유지한다.
같은 Z값이 겹치거나, 저장 모델과 다른 임시 Qt 위치·회전·배율·투명도·변환이 남은 장면도
기존 경로를 사용한다. 이 구성의 투명 합성에서 픽셀 차이가 발견되어 병렬 적용을 제한했고,
해당 제한을 회귀 검사했다. 실제 IVY 장면은 이 적용 조건을 통과한다.
FFmpeg 인코더 설정과 시각화·영상 디코더는 이번 변경에서 교체하지 않았다.

## 실제 IVY 표본

| 경로 | 20초 영상 내보내기 |
|---|---:|
| 기존 순차 캡처, 상세 계측 끔 | 49.406초 |
| 병렬 캡처, 상세 계측 끔 | 35.578초 |
| 최종 가사 분석 스냅샷 포함, 상세 계측 끔 | 35.172초 |
| 최종 빌드된 렌더 작업자 사용, 첫 실행 | 44.093초 |
| 최종 빌드된 렌더 작업자 사용, 재실행 | 36.187초 |
| 기존 순차 캡처, 후속 재측정 | 54.391초 |

두 병렬 실행의 중앙값은 35.375초로 비교 표본보다 약 28.4% 짧다. 준비 시간도 포함했다.
수정 전후 1,200개 디코딩 프레임·타임스탬프와 음성 PCM의 해시가 모두 같다.
빌드된 작업자 두 실행과 후속 순차 실행도 같은 해시였다. 빌드 검사는 소스의 격리된
UI 하네스가 각 렌더 작업자로 배포 실행 파일을 시작하는 방식이다. 재실행 시 작업자
3개가 실제 선택된 것을 기록했다. 설치본 UI 전체를 조작한 측정은 아니다.
첫 실행과 재실행 편차가 있으며 다른 사용자 앱의 부하를 고정하지 않았으므로,
28.4%를 설치본의 고정된 개선율로 보고하지 않는다.

Intel i5-14600KF/논리 CPU 20개/32GB, Windows, Python 3.12.15/PySide6 6.11.1,
1920×1080/60 FPS/NVENC/CRF 14/medium/AAC 320k다. 원본 프로젝트를 읽어 첫 곡만
20초로 줄인 격리된 복사본을 Qt offscreen으로 실행했다. 전체 트랙 수·진행 표시·종료
애니메이션은 단축본을 따른다. 상세 계측을 켠 초기 시제품 수치와 섞어 개선율을 계산하지 않았다.

## 검증과 한계

내보내기·가사·텍스트·도형 회귀 검사 28개 모듈, 392개 테스트에서 실패/오류가 없었다
(조건부 skip 9개). 실제 2작업자 취소/최종 인코더 실패와 종료 메시지 경계 검사까지
새 모듈의 7개 테스트를 별도 실행해 모두 통과했다. 불투명·알파 파이프의 픽셀 동일성,
글꼴, 작업자 강제 종료, 모든 자식 프로세스의 회수를 포함한다.

Windows 실행 파일을 실제 작업자 실행기로 지정하고 설치본의
`--multiprocessing-fork` 명령 형식으로도 최종 7개 검사를 통과했다. Python의 `-c` 시작 형식은
frozen 실행 파일과 다르므로 이 검증에서 사용하지 않았다. 최종 소스의 작업자·가사 분석
16개 검사는 조건부 제외 없이 통과했다.
4MB 분석 배열을 포함한 시작·취소 및 마지막 메시지 경계 검사의 재실행도 통과했다.
작업자 취소 후 부모의 큐 전송 스레드가 남는 경우도 검사했다. 부모가 사용하지 않는
작업 큐의 읽기 핸들을 닫아 중단된 수신자가 전송 스레드를 붙잡지 않게 했고, 종료 시
그 스레드까지 기다린다. 최종 작업자 모듈 7개 검사를 두 번 반복해 모두 통과했다.
배포 필수 파일 검사, 실행 파일 내부의 작업자 프로토콜·큐 정리 코드 포함 여부 검사와
기본 GUI `--smoke-test`(종료 코드 0)도 완료했다.
설치 파일은
`output-setup/export-parallel-canvas/Playlist Canvas-1.3.1.3-parallel-canvas-setup.exe`에
별도 생성했고 SHA-256 파일도 함께 기록했다. 사용자 설치본은 자동 교체하지 않았다.

전체 21분 완주, 여러 GPU 드라이버, 수십 분 메모리 안정성과 4K는 아직 검증하지 않았다.
렌더 프로세스별 Qt/NumPy/이미지 캐시를 보유하므로 메모리 사용은 늘어난다. 짧은 표본의
28.4%를 모든 프로젝트의 완료 시간 단축률로 보장할 수 없다.
