# 가사 검색 안정성과 단계별 가져오기 개선

## 확인한 원인

기존 구현은 별도의 가사 라이브러리를 사용하지 않고 Python `urllib`로 LiriQo의 단일 `/v1/lyrics` 엔드포인트를 호출했다. 제공자 선택은 요청을 분리하지 않고 응답을 로컬에서 필터링했다. 따라서 LiriQo의 HTTP 429는 제공자를 바꿔도 해결되지 않았다. 앨범 태그도 엄격하게 필터링하여 `GREENGREEN_playextended`처럼 실제 카탈로그 앨범과 다른 태그가 정상 결과를 제외할 수 있었다.

## 대안 비교와 선택

| 방식 | 장점 | 한계 / 결정 |
| --- | --- | --- |
| KuGou 직접 API | KRC에 기록된 단어·음절별 시간 정보 | 기본 통합 검색에 포함. 선택한 가사 ID로 다운로드하고 TTML로 변환 |
| AMLL TTML DB | 커뮤니티가 제작한 TTML 원문 및 검색 API | 기본 통합 검색에 포함. 선택한 ID와 파일명을 검증하여 원문 보존 |
| LRCLIB 직접 API | 동기화 가사를 제공하는 공개 API | 현재 검색 경로에서 제외. 과거에 읽은 가사 데이터는 계속 사용 가능 |
| LRCLib Python API 래퍼 | 검색과 ID 조회를 Python 메서드로 제공 | 동일 LRCLIB 서버를 사용하므로 래퍼 설치 자체가 서버 오류를 해결하지는 않음. 기존의 크기 제한, 타임아웃, 캐시, 취소, 요청 간격 처리를 유지하는 직접 연동을 선택 |
| LiriQo | 여러 제공자의 단어·음절 TTML 지원 | 하나의 중계 서버에 의존. 검색 엔드포인트와 호출 경로 제거 |
| LyricsGenius | Genius 검색과 가사 텍스트 접근 | 공식 문서상 가사 본문을 웹 페이지에서 스크래핑. 페이지 구조 의존이 있고 현재 앱에 필요한 동기화 가사의 대체 경로로 적합하지 않아 채택하지 않음 |

근거:

- [LRCLIB 공식 저장소](https://github.com/tranxuanthang/lrclib): 동기화 가사 서비스 및 API.
- [LRCLib Python API 구현 문서](https://lrclibapi.readthedocs.io/en/stable/_modules/lrclib/api.html): 동일 `lrclib.net/api`의 `search`, `get/{id}` 등 사용.
- [LiriQo 공식 저장소](https://github.com/AlFarrizi-Studio/LiriQo): 단일 엔드포인트 및 제공자별 동기화 지원.
- [LyricsGenius 동작 문서](https://lyricsgenius.readthedocs.io/en/master/how_it_works.html): 가사 본문은 Beautiful Soup로 페이지에서 추출.

## 최종 동작

1. 기본값은 KuGou·AMLL·LRCLIB 통합 검색이다. [2026-10-29 LRCLIB 복원](2026-10-29-lrclib-provider.md) 이후 세 공급원을 사용하며 개별 공급원 검색도 선택할 수 있다. 제목·아티스트로 조회하며 길이 입력란은 제거했다. 최초 가사 검색에는 길이를 조건으로 보내지 않는다. 선택한 플레이리스트 곡의 제목·아티스트가 그대로인 경우에만 기존 길이 메타데이터를 내부 정렬에 사용한다. 검색 정보를 수정하면 이 정렬 힌트도 제거한다.
2. KuGou 가사 후보 검색이 비면 곡 검색 API로 카탈로그의 제목·아티스트 표기를 확인한다. 중복을 제거하고 최대 세 녹음에 대해 카탈로그 해시·길이와 표준화된 이름으로 가사 후보를 조회한다. 이는 한글 아티스트명이나 제목만 입력하면 가사 후보 API에서 0개가 반환되는 경우를 복구한다. 사용자가 결과를 선택했을 때만 보존된 가사 ID·accesskey로 KRC를 다운로드한다. 원본 시간을 TTML로 변환하며 압축 해제 크기·구간·텍스트 오프셋을 검증한다. 단어 시간을 추정하지 않는다.
3. AMLL은 musicName / artistName으로 조회하며 가사 본문 전체를 검색하는 q를 사용하지 않는다. 아티스트 검색 결과가 없을 때만 제목으로 한 번 넓히고 안내한다. 결과 ID로 TTML을 가져올 때 파일명도 비교하여 다른 녹음이나 버전이 적용되는 것을 막는다.
4. 한 공급원의 연결·응답 실패는 경고로 표시하고 다른 공급원의 결과를 보존한다. 둘 다 실패하면 각각의 오류를 표시한다. 요청 간격, Retry-After, 크기 제한, 캐시, 취소를 유지하며 LiriQo·LRCLIB은 호출하지 않는다.
5. 검색 단계에는 동기화 방식을 추정 표시하지 않고 ‘선택 후 확인’으로 표시한다. 가져오기 완료 후 실제 단어 시간이 있으면 단어 동기화로 갱신한다. AMLL이 곡 길이를 제공하지 않는 경우 길이를 ‘—’로 표시한다. KRC는 TTML로 저장·적용하고 AMLL TTML은 원문을 보존한다.
6. 공급원에서 독립적으로 반올림된 단어 경계의 최대 1ms 겹침은 원본 값을 바꾸지 않고 허용한다. cue 범위를 벗어나거나 역전된 구간, 1ms를 넘는 겹침, 잘못된 텍스트 오프셋은 계속 거부한다.
7. 결과 화면에 성공한 공급자의 개별 검색 건수를 표시한다. 진짜 미수록·검색 실패·복구 성공 안내를 구분하며, 검색에 영향을 주지 않는 체크박스를 해제하라는 안내는 하지 않는다.

화면은 기존 가사 편집기와 동일한 `QStackedWidget` 방식의 마법사로 변경했다. 곡 정보 → 결과 선택 → 확인 및 적용 순서로 필요한 화면만 보여준다. 결과 선택 및 읽기가 완료되기 전에는 다음 단계로 진행할 수 없다. 이전으로 돌아가도 검색 조건과 선택한 가사를 보존한다. 복사·저장·적용은 확인 단계에 표시하고, 진행 중 취소는 모든 단계에서 가능하다. 검색 결과로 이동하는 것만으로 첫 번째 결과를 자동 선택하지 않는다.

## 검증 결과

- 관련 서비스, KRC 변환, 두 공급원, 대화상자, 메인 창 적용, TTML, 가사 형식, 응답성, 프로젝트 모델·저장 테스트 **140개 통과**. 카탈로그 표기 복구, 검색 확장 제한, 부분 실패, 취소, 원문·ID 보존, 캐시, 압축 해제 제한, 잘못된 시간 검증을 포함한다.
- 한글·영문으로 모든 단계를 **760×560** 최소 창 크기에서 확인. **960×680** 화면을 렌더링해 배치 확인.
- 실제 서버에서 기존 LiriQo의 HTTP 429 재현.
- 최종 코드로 `TNT / CORTIS`의 KuGou KRC를 TTML로 변환해 **40줄·231개 단어 시간 구간** 보존 확인.
- `TNT / 코르티스` 및 제목만 입력한 `TNT`가 기존 코드에서 0개를 반환하는 현상을 재현했다. 곡 검색 API를 통한 표기 복구 후 각각 **16개**로 회복됐다. 실제 Qt 검색 창에서도 길이 입력 없이 `TNT / 코르티스` → 16개 결과 → 231개 시간 구간 미리보기까지 확인했다. 이 곡의 AMLL 결과는 0개이므로 두 공급원 건수는 `KuGou 16 · AMLL TTML DB 0`으로 표시한다.
- 최종 코드로 `ME! / Taylor Swift`의 KuGou 결과 **72줄·483개 시간 구간**, AMLL 결과 **70줄·581개 시간 구간** 파싱 및 프로젝트 모델 검증 확인.
- AMLL `ME!`에 포함된 두 단어 경계의 1ms 겹침을 재현하고 원본 값을 유지한 상태로 가져오기 성공. 음원과의 청각적 동기 정확도까지 검수한 것은 아니다.
- 외부 서버 응답은 시점에 따라 달라진다. 이 변경은 서버 가동률의 보장이 아니라, 단일 중계 의존 제거와 실패 복구 및 녹음 확인 흐름의 개선이다.
