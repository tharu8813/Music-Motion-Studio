# 실시간 미리보기 렌더링 검증 · 2026-11-04

기준은 GitHub main의 666d64bf39ea6cd3a838f5d352b52912a00ff1f0이다. Windows 11, PySide6/Qt 6.12, OpenGL 3.3, RTX 5060에서 같은 벤치마크 도구로 전후를 실행했다. 기준 코드에는 수신 카운터와 toImage() 타이머만 덧붙여 관찰했다. 모든 비교의 해상도 우선 캔버스 배율은 1.000이고, 화면 목표는 60 FPS다. 미리보기 창은 960×700으로 열고 3초 예열 후 약 8초를 측정했다. 해상도는 캔버스 내부 래스터 크기다.

B·D·E·F에서는 편집기처럼 시각화 소스와 오버레이를 같은 Z 위치에 두었다. 합성 WAV의 120 BPM 펄스 시각을 분석 입력으로 사용하고 실제 AutoMix 계획과 FFmpeg FLAC 믹스를 미리 준비했다. 네 장면에서 Beat Match / Short Fade 전환 2개를 확인했다. 리듬 모델 분석 시간은 재생 측정 범위 밖이다. F의 전체 화면 왕복과 탐색·일시정지는 예열 전에 수행했다.

toImage() 열은 전후 값이다. 나머지는 변경 후 값이다. GL 타이밍은 CPU 호출 시간이다. Qt 합성 시작→교체 P95는 C에서 2.42 ms, E에서 4.76 ms였다. GPU 타임스탬프 쿼리와 물리 화면 스캔아웃 타이밍은 측정하지 않았다.

QGraphicsScene::render 호출 P95는 B 7.73 ms, D 11.29 ms, E 20.72 ms였다. D에서 CPU 영상 스케일링 P95는 0.91 ms, 색상·블러 처리 P95는 75.07 ms였다. E는 더 많은 장면을 표시해 초당 업로드량과 총 드롭이 함께 늘었다. 장면당 업로드량은 약 56.4→54.0 MiB였다. 움직이는 투명 밴드의 크기가 바뀌면서 B·D·E·F의 텍스처 재할당은 늘었다.

장면 시각에서 QMediaPlayer의 샘플 위치를 뺀 값은 F에서 −199~+68 ms였고 E에서 −271~−66 ms였다. 디코더 프레임의 원본 PTS와 요청 위치도 별도로 기록했다. 6초 영상의 반복 경계에서 PTS가 되감기므로 원시 차이에 주기만큼의 이상치가 포함된다. 오디오 장치 출력과 화면 사이의 물리적 동기 오차는 별도 측정이 필요하다.

이전 파이프라인은 시각화가 다른 소스 사이에 있을 때 전체 Canvas 준비와 Z 밴드 래스터를 같은 장면에서 수행할 수 있었다. 현재는 기존 순서형 밴드가 직접 영상과 시각화를 함께 받아 정적 배경·커버를 재사용한다. 키프레임의 현재 변환에 맞춰 투명 밴드의 범위를 계산하고, 정적 밴드는 동적 캔버스 배율이 바뀌어도 프리셋 래스터 해상도를 유지한다. 정적 캔버스 이미지 캐시 한도는 128 MiB다.

C에서 Qt가 준 프레임은 CPU에 있는 NV12였다. Qt 공개 매핑 API와 기존 GL 셰이더로 YUV를 전달해 CPU RGB 변환을 줄였다. NV12·NV21·YUV420P의 검증된 경우에 적용되며 영상 방향, 지원하지 않는 포맷과 스타일에 따라 기존 이미지·CPU 경로를 사용한다. 복수 영상의 우선 병목은 넓은 가사·파티클의 래스터/업로드, 블러를 포함한 CPU 필터, 큰 장면의 GUI 대기다. 측정된 4K 장면은 이전 보고서에 기록된 다른 입력과 환경의 수치와 직접 비교할 수 없다.

- 창을 20회 열고 일시정지·탐색·재생·종료했다. 매번 GPU 텍스처 할당이 0으로 돌아갔고 디코더·작업자 해제 검사를 통과했다. 첫 종료 후 대비 최고 RSS는 기준 +124.8 MiB, 변경 후 +104.8 MiB였다. 두 실행 모두 64 MiB 기준에서 실패했다.
- 실제 전체 화면 왕복, 포커스 전환 이벤트와 모의 GPU 컨텍스트 오류의 CPU 폴백을 검사했다. 전체 화면 커서 오버라이드 복원은 변경 후와 원본 main에서 모두 실패했다. 원본 main에서는 정지 커서 타이머 시험도 한 건 더 실패했다. 물리 키보드 Alt+Tab과 드라이버 수준 컨텍스트 손실은 재현하지 않았다.

## 후속 최적화

앞 단계의 작업 트리를 기준으로 같은 Windows 장치, 해상도 우선 배율 1.000, 동일한 C·D·E 입력을 다시 측정했다. 아래 FPS는 새 장면 표시다. D와 E의 측정에는 합성 음원의 박자로 만든 실제 FFmpeg AutoMix 오디오가 포함된다.

| 장면 | 신규 장면 FPS | 신규 장면 간격 P95 ms | 영상 매핑·패킹 P95 ms | 앱 CPU 코어 | 앱 RSS 최고 MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| C. 1080p/60 영상 | 53.6 → 52.9 | 33.0 → 34.9 | 6.3 → 6.0 | 0.83 → 0.78 | 490 → 487 |
| D. 1080p 복수 영상·블러 | 20.1 → 20.2 | 74.8 → 71.2 | 13.9 → 11.8 | 1.76 → 1.74 | 854 → 842 |
| E. 4K 복수 영상·가사·음악 반응 | 8.5 → 8.5 | 178.8 → 168.5 | 31.2 → 23.6 | 1.26 → 1.24 | 1,313 → 1,201 |

- 배율 1.000과 밀집 행 조건을 만족하는 CPU NV12·NV21은 Qt 매핑을 유지한 채 기존 텍스처에 전송한다. 패딩, 축소와 RHI 프레임은 기존처럼 소유한 버퍼를 사용한다. 축소 평면은 채널을 묶어 같은 위치에서 샘플링한다.
- GPU는 전송이 끝난 래스터 참조를 해제한다. 순서형 캔버스는 큰 동적 작업 이미지 한 장을 재사용하며, 이전 이미지가 보존되어야 할 때 QImage의 쓰기 시 복사를 사용한다. E의 별도 짝지은 실행에서도 매핑·패킹 P95가 34.7→20.6 ms로 줄었다. 신규 FPS 증가를 일관되게 관찰하지 못했다.
- 블러의 합과 나눗셈을 그대로 두고 임시 배열을 줄였다. 16개 입력에서 두 축의 커널 결과가 비트 단위로 일치했다. 540×304 단독 커널 P50/P95는 15.17/19.10→12.84/15.86 ms였다. D의 실제 재생에서 색상·블러 P95는 64.4→67.3 ms로, 단독 커널의 개선이 재생 지연 감소로 이어지지는 않았다.
- 20회 재개폐에서 후속 기준의 RSS 증가량은 CPU +100.2 MiB, GPU +154.4 MiB였다. 최종 GPU 실행에서는 +102.8 MiB로 64 MiB 기준을 넘었다. Qt 영상·오디오 플레이어와 싱크만 만든 별도 실험에서도 +59.7 MiB가 관찰됐다. 해제 후 유효한 미리보기 위젯·플레이어 수는 늘지 않았고 강제 Python GC로 RSS 증가가 해소되지 않았다. 종료 시 원본 파일 재열기를 생략하는 실험은 두 백엔드에서 일관되게 개선되지 않아 적용하지 않았다.
- 60초 재생 직후 종료가 멈춘 스택에서 GUI의 플레이어 정지와 디코더의 메일박스 신호가 동시에 진행 중인 것을 확인했다. 싱크 분리 순서만 바꿨을 때도 멈춤이 재현됐다. 최종 경로는 Qt GUI 이벤트 큐에서 미디어 소스를 해제하고, 해제가 끝난 뒤 비디오 싱크를 분리한다. 변경 후 60초 실제 재생은 수락 1,795프레임, 압력 드롭 3개를 기록하고 정상 종료했다.
- Windows에서 QTest의 마우스 이동이 위젯의 MouseMove 이벤트를 보내지 않는 경우를 확인했다. 커서 복원 테스트는 Qt 이벤트를 직접 전달해 검증하고, 데스크톱 포인터 위치 폴링은 별도 기존 테스트에서 검증한다.

후속 회귀는 오프스크린 106건 통과·0건 실패·5건 건너뜀, Windows 네이티브 46건 통과·2건 실패·0건 건너뜀이다. 네이티브 실패는 20회 재개폐 RSS 기준과 원본 main에서도 실패한 정지 커서 타이머 검사다. 변경한 커서 복원 테스트는 통과했다.

짝지은 측정 원본은 build/preview-followup-final-{base,after}-{C,D}.json 및 build/preview-followup-scratch-{base,after}-E.json에 있다. 재개폐 대조와 Qt 단독 실험의 원본은 build/preview-followup-repeat-*.log, build/preview-reset-trial-*.log, build/preview-qt-media-probe.log에 있다. 최종 종료 경로의 회귀 로그는 build/preview-followup-queued-*.log에 있다.
