# Music Motion Studio 렌더링 및 사용 성능 검증

2026-11-04 · 기준 코드 `755cdeb` · Windows 11, 논리 CPU 20개, Python 3.14.10,
PySide6 6.12.0, NumPy 2.5.4, FFmpeg 9.0.2. 새 프로세스에서 격리된 설정과 생성한 미디어를 사용했다.
원본 프로젝트, 앱 버전, 사용자 설정, 자동 업데이트, 인코더 기본값은 변경하지 않았다.

4K 영상 3개를 사용하는 CPU 미리보기에서 가장 큰 문제가 발견됐다. 필터에는 최신 프레임만
유지하는 제한이 있었지만, 필터에 도착하기 전 GUI 큐에는 큰 디코더 프레임이 계속 쌓일 수 있었다.
큐 앞단에 영상별 최신 프레임 한 개와 GUI 알림 한 개만 유지하도록 하자, 측정 구간 내 장면을
거의 표시하지 못했던 사례가 **중앙값 6.27 FPS**로 개선됐다. 측정한 최대 RSS의 중앙값은
**6.04 GiB → 1.46 GiB**였다. 이 고부하 미리보기는 개선 후에도 60 FPS에 도달하지 못했다.

오디오 주파수 분석, Canvas 작업자 메시지, 필터 이미지 캐시도 개선했다. 1080p 예제의 전체 내보내기는
이번 측정에서 빨라졌고, 4K 내보내기에는 재현 가능한 속도 개선이 없었다. 비교한 내보내기 MP4는
1080p와 4K 각각 파일 전체의 SHA-256이 전후 동일했다.

## 실제 경로와 확인한 병목

| 영역 | 확인한 경로와 판단 |
|---|---|
| 영상 내보내기 | `ExportController` → `ExportPlan`/`ExportTimelinePlanner` → `ExportSession`/`ExportCanvasCapturer` → Canvas별 제한된 큐와 파이프 또는 중간 파일 → `FFmpegRenderer`의 합성·인코딩·Mux. 이전 코드에도 Qt 장면의 독립 프로세스 렌더링과 FFmpeg 동시 실행이 있어 프레임 버퍼나 작업자 수를 늘리지 않았다. |
| FFmpeg | `filter_graph.py`는 이미 같은 경로와 같은 미디어 시작 위치의 입력을 합치고, 중립 색상/알파 필터를 생략한다. 자막, 색상, 회전 또는 투명도에 영향을 줄 수 있는 필터 순서와 출력 설정은 유지했다. |
| 미리보기 | `ExportPreviewDialog` 및 `MotionPreviewMedia`의 시계/탐색 → `SourceItem`의 Qt 디코더 → 이미지 변환·필터 → Canvas 또는 `GpuTexturePreviewSurface`. 변경 전 4K CPU 측정 한 회에서 영상 콜백 1,509회의 포괄 벽시계 합이 35.29초였으며, 실제 장면 렌더링 5회의 합은 0.032초였다. 해당 합에는 준비 구간이 포함되며 서로 겹치는 계측은 더하지 않는다. |
| GPU | 네이티브 OpenGL에서 텍스처 재사용·예산·정리와 기존 CPU 폴백을 유지했다. 이 장비의 측정 영상은 `NoHandle`이어서 디코딩부터 표시까지의 GPU 전용 경로가 검증된 것은 아니다. |
| 오디오 | `PythonVisualizerRenderer`의 디코딩/FFT는 Canvas 반응 준비와 시각화에 사용된다. AutoMix BPM/비트는 별도 분석 서비스다. 같은 파일에 대한 AutoMix의 경로 중복 제거와 분석기 버전별 캐시는 이미 작동하므로 이를 유지했다. |
| 시작·저장·UI | `MainWindow` 준비, `ProjectService`의 패키지 저장·검증·열기, 편집/미리보기 타이머를 확인했다. 프로젝트 저장 형식, 분석 모델의 지연 초기화, 패키징은 변경하지 않았다. |
| 배포 | PyInstaller spec은 Qt Multimedia/OpenGL과 필수 ONNX 리소스를 포함하며 의존성 테스트와 무거운 PyTorch 분석기를 제외한다. FFmpeg의 기존 설치·탐색 방식을 유지했다. 이번 작업에서 설치본은 재빌드하지 않았다. |
| 취소와 출력 보호 | 기존 FFmpeg 종료, Canvas 큐 백프레셔, 작업자 정리 및 같은 폴더의 임시 출력 파일을 성공 시 교체하는 경로를 유지했다. 새로운 프레임 유실 정책은 실시간 미리보기에만 적용된다. |

첫 4K 비교는 24.622 → 27.681초로 12.4% 느려졌다. 도구 수정 이후 같은 입력으로 변경 전의
정확한 소스를 부모와 Canvas 자식에 다시 불러 순서를 뒤집어 재비교한 결과, 차이는 0.9%였다.
초기 결과도 원본 JSON에 남겼다. CPU 부하·클럭과 전원 상태를 고정하지 않아 4K 속도 개선이나
특정 코드 변경의 회귀로 단정하지 않는다. 최초에 요청과 달리 실제 1080p였던 4K 도구 실행은
비교에서 제외했다.

기존 도구는 상위 임시 폴더와 그 하위 출력 폴더를 함께 훑어 일부 임시 파일 크기를 중복 합산했다.
도구에서 이를 수정했으며, 초기 JSON의 `peak_temp_bytes`는 참고 기록으로만 남겼다.
파일 읽기·쓰기 처리량은 측정하지 않았다.

Windows 네이티브 OpenGL 3.3, RTX 5060에서 4K 영상 3개를 각 1회 비교했다. 10초 측정 구간을
요청했으나 기준 코드는 이벤트 처리가 밀려 20.45초 후 측정을 마쳤고, 새 장면은 1회 표시했다.
수정 코드는 10.03초 동안 **8.48 FPS**, 표시 간격 P95 **124.92 ms**를 기록했다. 앱 RSS의
샘플 최대는 **32.30 → 1.97 GiB**였다. 두 실행의 텍스처 할당 최고치는 47.39 MiB였다.
GPU 사용률, 전체 VRAM 사용량과 GPU 작업 완료 시간은 미측정이다. 마지막 CPU와 GPU 실행의
앱 프로세스 평균 CPU 시간은 각각 논리 코어 **1.60개분**과 **1.64개분**이다. 이 실행부터
영상별 수락·드롭 수와 CPU 시간을 기록했으므로 해당 지표의 전후 수치는 제공하지 않는다.

## 남은 병목과 측정 범위

1. **4K 다중 영상 미리보기 (P0).** GUI 이벤트 적체는 줄었지만 디코딩 후 전체 프레임을 이미지로
   바꾸는 콜백의 P95는 한 쌍의 프로파일에서 24.8 → 24.5ms였다. 영상별 픽셀 변환과 업로드의
   비용을 줄여야 목표 FPS에 가까워질 수 있다. 테스트 영상 3개는 같은 파일을 별도 레이어에서
   재생했으며, 서로 다른 재생 시각·속도를 고려해 디코더 공유는 도입하지 않았다.
2. **4K 내보내기 (P0).** 캡처와 인코딩이 이미 겹쳐 실행된다. FFmpeg 합성, 인코딩, 디코딩 각각의
   CPU 사용률을 분리하고, 여러 실제 영상·가사·파티클을 포함한 긴 프로젝트에서 병목을 재확인해야 한다.
3. **다양한 프로젝트와 장치 (P1).** 실제 30곡 장시간 내보내기, 여러 디스플레이, Alt+Tab, 배율 변경,
   드라이버에 의한 컨텍스트 손실, Intel/AMD 인코더, 설치 프로그램 시작은 이번 측정 범위 밖이다.
   AutoMix Beat This/ONNX 및 Sonara의 분석 시간을 Basic 벤치마크 수치로 대체하지 않는다.

## 출력 및 회귀 검증

- 1080p/30과 4K/60 MP4를 FFmpeg로 다시 디코딩했다. 각 전후 쌍은 전체 180프레임과 360프레임의 픽셀 해시, 각 프레임의 시간 정보, 6초 길이, 48kHz 스테레오 PCM이 일치했다. 4K 출력은 채널당 288,000샘플이며, 첫 비영 샘플의 위치, 피크 및 RMS도 일치했다.
- 실제 FFmpeg를 사용하는 회귀 실행에서는 AutoMix, 크로스페이드, 투명 Canvas 레이어와 가사·키프레임 픽셀 비교, 작업자 취소와 인코더 실패 정리가 통과했다. 프로젝트 패키지와 모션 편집의 기존 회귀 테스트도 통과했다.
- 마지막으로 프레임 큐, 직렬화, FFT, 캐시 예산, Canvas 작업자와 실제 FFmpeg 스트리밍에 집중한 25건을 다시 실행해 모두 통과했다. 이 재실행은 저장소 전체 건수와 별도로 기록했다.
- 저장소 회귀는 2,419건 실행에 2,395건 통과, 18건 건너뜀, 6건 실패였다. 실패 6건은 영어로 설정했을 때 기준 코드와 수정 코드에서 동일하게 재현됐고, 한국어로 설정하면 두 코드 모두 통과했다. 최초 전체 실행은 샌드박스가 로컬 OAuth 콜백 연결을 거부해 중단했다. 후속 실행에서 해당 인증 테스트 3건을 제외했다.
- Windows 네이티브 GPU 검증은 35건 중 34건 통과했다. 오류 1건은 전체 화면 오버레이를 다시 붙인 뒤 커서 오버라이드가 없었던 테스트이며, 같은 Windows 환경의 기준 코드에서도 동일하게 재현됐다. 60초 GPU 재생은 1,200프레임을 수락하고 압력 드롭 5건을 기록했다. 준비 이후 RSS 증가의 관측 최대는 9.43 MiB였다.
- 같은 프로세스에서 GPU 미리보기를 20회 열고 일시 정지, 탐색, 재생, 종료했다. 매회 종료 시 텍스처 할당이 0으로 돌아가고 디코더가 해제됐다. 첫 종료 이후 RSS 증가의 관측 최대는 62.78 MiB로, 이 테스트의 64 MiB 기준에 근접했다. 더 긴 반복에서 같은 수준으로 유지되는지는 별도 측정이 필요하다.
- RTX 5060에서 `h264_nvenc`를 명시한 1080p/30 내보내기를 실행했다. 4.58초에 180프레임을 생성했고, FFprobe로 출력 파일의 실제 인코더 태그를 확인했다. 인코더 선택 경로의 동작 확인에 사용한 단일 실행이다.
- 10분 음원의 음악 반응 준비를 취소했을 때, 취소 콜백부터 준비 종료까지 3.14ms가 걸렸다. 출력 엔벨로프는 생성되지 않았다. 전체 내보내기 취소와 파이프 정리는 별도 회귀 테스트에서 확인했다.
