# 속도·메모리 최적화 — 2026-10-25

기존 비주얼라이저 직접 전송과 작업 트리의 다른 변경을 유지하면서 아래 다섯 경로를 개선했다. 새 의존성, 프로젝트 형식 변경, 화질·FPS 하향은 없다.

## 변경

- 실행취소 기록은 이전 기록과 같은 최상위 데이터 영역을 공유하고 변경된 영역만 JSON 복사한다. 공유 객체는 내부에만 보관하고 Undo·Redo 반환값은 계속 분리해서 복사한다. 곡이나 가사가 실제로 바뀌면 playlist 영역을 새로 복사한다. GUI의 프로젝트 직렬화 자체는 여전히 수행한다.
- 파티클·파형·레벨 미터만 있는 내보내기는 사용하지 않는 FFT를 생략한다. 파형과 스테레오 RMS 계산은 필요한 경우 그대로 수행하며, 주파수 비주얼라이저가 함께 있으면 FFT도 유지한다.
- 오디오 PCM을 float32로 변환한 뒤 같은 배열에서 정규화해 추가 float32 배열을 만들지 않는다. 부호와 진폭은 동일하다.
- 프로젝트 패키지를 다시 열 때 추출 캐시의 크기와 전체 CRC32를 확인한다. 일치하는 파일은 다시 추출하거나 교체하지 않고, 누락·손상 파일만 원자적으로 복구한다. 디스크 여유 공간도 재추출할 파일만 계산한다. 캐시 CRC를 읽는 작업은 남으며 기존 경로·중복 파일 검사와 취소 처리는 유지한다.
- 내보내기 프레임 일정은 반복 가능한 생성기로 만들고, 밀집한 시간 구간은 정렬된 수열을 병합해 순서대로 읽는다. 인접한 동일 장면도 한 개의 다음 장면만 보관하며 병합한다. 파이프·중간 영상·PNG 캡처가 모두 이 일정을 사용하고, 준비 진행률은 준비한 영상 길이로 계산한다. 기존 리스트 반환 API는 유지한다.

메모리는 tracemalloc로 추적한 Python·NumPy 할당이다. 프레임 일정은 이전·이후 모두 216,000개 상태를 생성한다. 기존 구현과 순차 재생·공백·크로스페이드·재생 속도 변경 및 24·30·60FPS를 조합한 72개 조건에서 모든 샘플 필드가 정확히 일치했다.

프로젝트 직렬화 시간은 약 24~26ms로 남아 있다. 이번 실행취소 시간 감소를 직렬화까지 제거한 것으로 해석하면 안 된다. 파티클·레벨 미터·파형의 렌더링 픽셀과 PCM 변환 결과도 비교했으며, 캐시 재사용·같은 크기의 손상 복구·취소 시 기존 미디어 보존·Undo/Redo 분리를 회귀 검사한다.

실제 장시간 4K·NVENC 성능은 이 측정에 포함되지 않는다. 실행 파일과 설치 프로그램은 재빌드하지 않았다.

## 검증 결과

관련 26개 테스트 모듈의 마지막 실행 결과가 모두 통과했다. 총 530개 검사 중 524개 통과, 6개 조건부 생략이다. 캐시 재사용 완료 직후의 취소 경계 사례를 수정하고 해당 회귀 검사를 재실행했다. 단일 파이프 전용 모의 내보내기 검사는 밴드 구성을 명시하도록 고쳐 최신 캔버스 분리 경로와 독립적으로 검사한다. 원본은 [테스트 결과](benchmarks/2026-10-25-speed-optimization-tests.json)에 보관한다.

실제 FFmpeg를 사용하는 3초·640×360·30FPS 내보내기는 파이프·중간 영상 경로 모두 90프레임을 출력했다. 이 검사는 두 경로의 동작 확인이며 이번 변경 전후의 전체 내보내기 속도 비교가 아니다. `compileall`과 변경 파일의 `git diff --check`도 통과했다.
